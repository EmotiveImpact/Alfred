## Executive assessment

ALFRED now has an integrated local application, not merely an interface mock-up or disconnected design assets. The refined console can consume backend records, selection supplies conversation context, reviewed memory and executive records have working interfaces, and bounded local jobs have durable state.

That is not the same as a production private-data release, a general-purpose reasoning agent, a native desktop application or an always-on cloud platform. Those remain distinct delivery gates.

Preserve the current architecture. The next increment should close access-control, private-storage, recovery and evidence-quality gaps before expanding deployment. Native packaging can be developed separately; it is not what makes the core always on.

This is a read-only source-and-evidence review. I inspected current GitHub main, selected implementation and tests, planning documents, CI logs, test reports and screenshots. I did not rerun the full application suite, test your hardware, inspect every source line, conduct a penetration test or certify the application. No repository files, PRs, settings or deployments were changed.

## 2. What is actually implemented

### Connected console and graph

`console/src/integration/deskClient.ts` now implements actual same-origin session, workspace, projection and inspection requests. `alfred/desk_http.py` serves the production console build at `/console/` and routes the projection endpoints to `alfred/console_api.py`.

The Python projection consumes the existing knowledge, reviewed-memory and executive services. Authored references, reviewed relationships, supporting evidence and executive links have distinct layer labels. Meaningful records carry stable IDs and evidence metadata; decorative geometry is not supplied as knowledge.

The relevant HTTP tests exercise a real backend and synthetic vault, not merely a frontend provider. This proves the connection exists. It does not prove that the user's actual projects or private accounts have been imported.

Current workspace discovery explicitly returns **one workspace per credential**. It is not yet the eventual unified multi-workspace/person/team experience.

### Memory and local action flows

The merged implementation includes stable selected-vault identity, reviewed-memory context, inspectable capture proposals, separate acceptance, valid periods, disputes, withdrawal and supersession history. Approved inbox notes use a create-only capability rather than unrestricted edits to human files.

Forgetting and whole-source removal have receipts and affect dependent current views; restore replays the retained lifecycle journal. These are meaningful controls, but they are not a guarantee of secure erasure or complete deletion across all backups and exports. Application encryption remains unimplemented in the reviewed checkpoint.

### Executive work and routines

Goals, priorities, commitments, decisions, milestones and follow-ups are backend records. The console uses those same records, rather than retaining a second fictional source of progress. Preparation briefs and cross-project insights are assembled using stated rules and permitted records. They should not be described as evidence that a model understands a business autonomously.

Routines include commitment review and morning briefs, schedules, budgets, quiet hours, pause and inspectable outcomes. Their current delivery is inside the application. They depend on the foreground host remaining operational.

### Jobs, cache and local runtime

The job architecture includes a coordinator, leases, heartbeats, cancellation, bounded retries, event cursors, result lineage and a bounded content-addressed cache. Clients can reconnect to job state.

The actual worker remains a **local subprocess executing allowlisted first-party job kinds**. It is not a remote computer, isolated VM, untrusted-code sandbox or general coding agent. The cache is local; it does not establish a cloud-mounted file service.

### Other bounded capabilities

Device pairing uses separate credentials and single-use codes. Source grants and revocation workflows exist, but legacy broad-scope defaults and separate per-device review histories remain.

Calendar/contact connectors read selected `.ics` and `.vcf` exports. They are not live Google, Microsoft or Apple account connections. Read-aloud is output only; microphone capture and speech input are absent. A specialist capability contract has a synthetic adapter, not real ENDSTATE, Noir, Loc8, 8BALL or God's Eye integrations.

## 3. Audit findings

### A. Confirmed: authoritative planning text is stale

The problem goes beyond an old PR label. README and the checkpoint describe PR #18 as unmerged. The requirement register's merge fields still describe branch-only work. The top of the PRD and applicable agent instructions still describe a disconnected console and planned capabilities that now have implementation. The security document retains early prototype descriptions of missing authentication and a future outbox.

The actual source and main commit establish a different state. A new builder following those status claims could repeat completed work or misunderstand which security paths actually exist.

**Recommended correction:** make one post-merge documentation change updating present-tense status in README, AGENTS, PRD, SESSION_HANDOFF, the checkpoint, security overview, remaining plan and register. Keep historical receipts as historical evidence, not overwritten claims. Do not promote partial functionality to complete merely because its source merged.

The register still reports 8 implemented, 24 partial and 1 not started across 33 requirements. That is its bounded classification, not an independently verified whole-product completion percentage. Passing the register checker verifies consistency, not the sufficiency of every implementation.

### B. Review required: approval projection may bypass source-level visibility

In the inspected `projection()` path, notes are obtained through permission-aware services, but approval rows are selected from `actions` by workspace and serialised with their text and destination path. The loop does not visibly apply the caller's equivalent source-read check. `action_view()` returns the stored parameters; a `mine` flag identifies ownership but is not itself a filter. The handler returns the projection as produced.

This is a **source-review concern, not a reproduced exploit**. It warrants a targeted test before private or shared use. It is about potential disclosure, not a demonstrated ability to approve someone else's action.

**Required test:** create an approved/read-restricted source and a proposal derived from it; authenticate a different person in the same workspace who lacks the source grant; inspect projection and related views before and after revocation. Check that text, paths, identifying metadata and restricted counts are withheld according to the intended policy. Decide and document any deliberately shared action visibility rather than assuming workspace membership grants all source access.

References: `alfred/console_api.py` approval assembly in `projection()`; `alfred/local.py` `action_view()`; `alfred/desk_http.py` console projection route. The sampled projection tests cover owner approval display and graph filtering, but that does not establish this different negative case.

### C. Confirmed: strict grants are not the default in the reviewed policy

`policy.permitted()` returns read/model capability availability under the legacy scope policy when no strict policy is configured. Other role and runtime checks still apply; this is not a claim that every user can invoke every model. It does mean the current system is not universally default-deny at the source-grant layer.

**Recommended correction:** define a migration for existing installations, explicitly grant the demonstration owner the required sources, make new installations and credentials default-deny, and exercise source permissions across graph, questions, approvals, jobs, exports, health and routines. Do not remove compatibility without migration tests.

### D. Confirmed evidence gap: relevance and reasoning are not mature

The committed M06 evaluation uses 44 synthetic questions. It reports keyword mean evidence recall of 0.9229 versus FTS5 at 0.9042, but approximately 76% of returned evidence items are irrelevant. All four unanswerable controls returned evidence. The report attributes much of this to context assembly and link expansion, not the choice of ranker.

That does **not** mean 76% of answers are wrong. It means the sampled retrieval packets contain substantial distracting context. The evaluation did not run a model or measure answer correctness.

The separate INT-002 receipt measures literal word coverage and support accounting on 13 source-mode cases. It explicitly does not establish semantic entailment, paraphrase handling or general contradiction detection.

**Recommended correction:** preserve the lexical baseline, improve relevance thresholds and link selection, allow genuinely unsupported queries to return no supporting material, and measure held-out cases. Evaluate an authorised reasoning runtime separately without bypassing earlier platform restrictions.

References: [M06 evidence](https://github.com/EmotiveImpact/Alfred/blob/75947b8dd59a3161c862d2533850a032994778e2/docs/evidence/memory-m06/RECEIPT.md), [INT-002 evidence](https://github.com/EmotiveImpact/Alfred/blob/75947b8dd59a3161c862d2533850a032994778e2/docs/evidence/int-002/RECEIPT.md).

### E. Confirmed: local execution is not a hosted always-on product

`DeskHTTPServer` binds to `127.0.0.1`; the module describes itself as a loopback development desk, not hosting. Host health explicitly reports that a foreground process is required and no installed service exists.

A VPS can host a process, but that fact does not supply ALFRED's missing remote authentication, device transport, service lifecycle, isolated workers, recovery, cloud-file tier or private-data safeguards. Do not expose this listener publicly by changing its bind address or stripping its checks.

**Recommended correction:** define and implement an explicit hosted mode with an appropriate authenticated transport and equivalent policy protections, supervised service lifecycle, restart/restore evidence and a separately enrolled worker. Desktop packaging is a parallel client concern, not the prerequisite for cloud operation.

## 4. What remains before the promised product

| Gate | Significant missing or partial work |
|---|---|
| Private pilot | Application encryption and key custody; strict defaults; complete deletion/export/restore accounting; cross-device identity/history semantics; documented and tested host recovery |
| Useful assistant | Better relevance; evaluated reasoning; PDF/office ingestion; capture policies; one real official connector workflow; actual microphone/transcription only with consent |
| Always-on and distributed | Installed service; authenticated remote mode; a second real node; isolated execution; provider integration; cloud-backed files; operational monitoring and recovery |
| Native and device experience | Signed desktop packaging, installer/update policy, OS integration, actual device acceptance; the proposed Tauri architecture is not a shipped app |
| Teams and specialist products | Multi-owner/role-limited sharing; actual specialist interfaces and adapters; independent security acceptance appropriate to deployment |

These gates are already largely represented in the remaining plan. Correct stale status and sharpen acceptance rather than creating another competing roadmap.

## 5. Recommended next implementation order

1. Reconcile main's status documents and add the approval-visibility negative test. Investigate the finding and correct it if reproduced. Preserve the exact current green baseline.
2. Complete the private-pilot controls: key custody/encryption, strict grants with migration, deletion/export accounting, restart and backup/restore acceptance. Use synthetic data until those controls pass.
3. Improve context relevance in parallel, then exercise one permitted end-to-end personal workflow: select a project, ask, inspect support, remember, correct, forget, restart and restore. Measure usefulness rather than adding more surface area alone.
4. Build the always-on deployment increment explicitly: supervised core, authenticated client/node connection, one bounded second-machine job, failure recovery, then an encrypted remote file tier and isolated workers. Native packaging may proceed independently once its client contracts are stable.

The owner's decisions should focus on data location, privacy/egress, key recovery, spending, accounts and material product choices. Ordinary implementation choices should come with an engineering recommendation rather than becoming an excuse to stop all work.

## Bottom line

The integrated architecture is worth keeping. The main branch and its CI provide real implementation evidence. The next priority is to make that integrated application trustworthy and operationally reliable, not to confuse a green test suite, a desktop wrapper or a rented VPS with the completed ALFRED platform.
